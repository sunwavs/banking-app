# RIS — Banking Web Application

A server-rendered banking web application built with Flask, PostgreSQL and Redis. It provides a customer
account area, money transfers between accounts, per-account transaction history, an investment catalog with
stock tracking, a basket and orders, and monthly reports for bank staff, all behind role-based access control.

The UI language is Russian.

## Features

**Customers (`external` role)**
- Personal account page with the list of accounts and balances.
- Money transfer between accounts with server-side validation of the amount, sender and recipient.
- Transaction history for a selected account and month, with incoming and outgoing operations distinguished.
- Investment catalog with stock levels, basket and order placement.

**Staff (`manager`, `analyst`, `operator` roles)**
- Two monthly reports: total amount sent per account and number of transfers per account.
- Reports are generated by database stored procedures, persisted, and can be listed and viewed by month.
- Report creation is restricted to the `analyst` role; viewing is available to `manager` and `analyst`.

## Technical highlights

**Data integrity (enforced by the database)**
- Money is `numeric(18,2)` everywhere (domain `money_amount`) and `Decimal` in the application: no
  floating-point rounding errors.
- A remittance is processed by two triggers. A `BEFORE INSERT` trigger locks both accounts in a fixed order, so
  concurrent transfers on one account are serialized and opposite transfers (A→B and B→A) cannot deadlock. An
  `AFTER INSERT` trigger verifies the balance and moves the money. The lock is taken before the insert on purpose:
  the foreign keys take shared row locks first, and two transactions upgrading them to exclusive locks would
  deadlock (reproduced and covered by a test).
- Constraints back the rules up: `balance >= 0`, `amount > 0`, sender ≠ receiver, foreign keys on both accounts,
  and an append-only ledger (a remittance can never be updated or deleted).
- Account numbers share one domain (`account_number`, 8–12 digits) and contract numbers one type in every table,
  so column types cannot diverge.
- Report procedures are idempotent (`ON CONFLICT DO NOTHING` on a unique `(month, account)` pair) and run in a
  transaction: a report is stored completely or not at all.
- Orders take goods from the stock atomically (`UPDATE … WHERE prod_balance >= n`) in the same transaction as the
  order; product rows are locked in a fixed order. Orders are linked to the user who placed them.
- Passwords can only be stored as bcrypt hashes: a `CHECK` constraint rejects anything else, and
  `hash_password()` produces a hash in SQL.

**Security**
- All SQL is stored in `.sql` files and executed with named parameters (`%(name)s`); no string interpolation.
- bcrypt password verification with equalized response time for unknown logins; login attempts are rate-limited.
- The session cookie holds only the user id. The user is read from the database on every request, so a changed role
  or a deactivated account (`users.is_active`) takes effect immediately.
- CSRF protection on all state-changing requests; logout, order placement and basket changes are POST-only.
- Strict `Content-Security-Policy` (same-origin only, no inline styles or scripts), `X-Frame-Options`,
  `X-Content-Type-Options`, `Referrer-Policy`, `Cache-Control: no-store` on pages, HSTS when served over HTTPS.
- Account ownership is verified on the server for transfers and history; account numbers submitted by the client
  are never trusted. Reverse proxies are supported (`PROXY_HOPS`) so the rate limit sees the real client address.

**Architecture and reliability**
- Application factory (`create_app`), blueprints per feature, and a layered structure:
  routes → repositories → database. The money rules live in one place, the database.
- A single permission model (`role → permissions`); the roles are an enum in the database and are checked against
  the manifest by a test. Unauthenticated requests are redirected to login, insufficient permissions return HTTP 403.
- Lazily created PostgreSQL connection pool; exceptions are propagated, transactions are rolled back, and database
  unavailability is reported as HTTP 503 (error pages render even then).
- Redis caches the product catalog with an atomic TTL and is invalidated when the stock changes. If Redis is
  unavailable or returns a corrupt value, the application falls back to the database.
- Report types are described by data (`REPORT_TYPES`); a new report requires a registry entry and three SQL
  files rather than new routes and templates.

## Transfer processing

1. The form input is validated: amount format and range, account number format, sender ≠ recipient.
2. One statement inserts the remittance only if the sender account belongs to the signed-in client
   (`INSERT … SELECT … WHERE contract_num = …`); otherwise nothing is inserted.
3. The `BEFORE INSERT` trigger locks both accounts in a fixed order.
4. The foreign keys verify that both accounts exist; the `AFTER INSERT` trigger checks that the balance covers the
   amount and moves the money. The whole balance may be transferred.
5. Database errors are translated into messages for the user (insufficient funds: `RIS02`; unknown recipient:
   foreign key `remittances_receiver_fkey`). Any error rolls the transaction back. On success the client is
   redirected (Post/Redirect/Get).

## Database

[`db/schema.sql`](db/schema.sql) creates the whole database and [`db/seed.sql`](db/seed.sql) fills it with
synthetic sandbox data. Both run in one transaction and never drop anything; to start over, recreate the database.

| Object | Purpose |
|---|---|
| `clients` | Bank clients (`contract_num` is the key) |
| `accounts` | Accounts with `balance` and the owning `contract_num` |
| `users` | Everyone who signs in: clients (role `external`, linked to a contract) and staff |
| `remittances` | Append-only ledger of transfers (`amount`, `remittance_moment`, sender and receiver account) |
| Triggers `on_transfer_lock`, `on_transfer`, `remittances_append_only` | Serialize, verify and apply a remittance; forbid changing the ledger |
| `products`, `orders`, `order_details` | Investment catalog with `prod_balance` stock, orders (with `user_id`) and order lines |
| `sent_report`, `transfer_count_report` | Stored monthly reports, one row per account and month |
| Procedures `create_sent_report(date)`, `create_transfer_count_report(date)` | Generate a report for the month of the given date |
| Function `hash_password(text)` | bcrypt hash for creating users in SQL |
| Types `account_number`, `money_amount`, `user_role` | Shared domains and the role enum |

Errors raised by the database for the application: `RIS02` (insufficient funds), `RIS03` (an attempt to change or
delete a remittance). Calendar months used by the reports and the application are months in the session time zone
(UTC by default, `DB_TIMEZONE`).

Sandbox data: three clients, four accounts, six transfers in January and February 2024, three products and six
users. Every user has the password `sandbox-password`; this is for local use only.

| Login | Role |
|---|---|
| `client1`, `client2`, `client3` | `external` (contracts `1001`, `1002`, `1003`) |
| `manager1` | `manager` |
| `analyst1` | `analyst` |
| `operator1` | `operator` |

Reports can be generated for 2024-01 and 2024-02.

## Getting started

Requirements: Python 3.11+, PostgreSQL 13+ (for the trusted `pgcrypto` extension), Redis (optional; set
`CACHE_ENABLED=false` to run without it).

**PostgreSQL and Redis with Docker** (the sandbox database is created automatically):

```bash
docker compose up -d
```

**Or with an existing PostgreSQL server:**

```bash
createdb Bank
psql -v ON_ERROR_STOP=1 -d Bank -f db/schema.sql -f db/seed.sql
```

**The application:**

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env        # set SECRET_KEY and the database parameters (DB_PASSWORD=postgres for Docker)

flask --app wsgi run --debug                  # development
gunicorn -w 4 -b 0.0.0.0:8000 wsgi:app        # production, behind an HTTPS proxy
```

Then sign in as one of the sandbox users above.

Production notes: set `SESSION_COOKIE_SECURE=true` (this also enables HSTS); set `PROXY_HOPS` to the number of
reverse proxies in front of the application; with several workers use a shared `RATELIMIT_STORAGE_URI` (for example
Redis).

## Configuration

All settings are read from environment variables (see [`.env.example`](.env.example)).
The application refuses to start without `SECRET_KEY`.

| Variable | Default | Description |
|---|---|---|
| `SECRET_KEY` | — (required) | Session signing key |
| `DB_HOST`, `DB_PORT` | `127.0.0.1`, `5432` | PostgreSQL address |
| `DB_USER`, `DB_PASSWORD`, `DB_NAME` | `postgres`, empty, `Bank` | PostgreSQL credentials and database |
| `DB_TIMEZONE` | `UTC` | Time zone of the database session; defines the boundaries of calendar months |
| `DB_POOL_MIN`, `DB_POOL_MAX` | `1`, `10` | Connection pool size per process |
| `DB_CONNECT_TIMEOUT` | `5` | Connection timeout, seconds |
| `CACHE_ENABLED` | `true` | Enable the Redis cache |
| `REDIS_HOST`, `REDIS_PORT`, `REDIS_DB` | `127.0.0.1`, `6379`, `0` | Redis address |
| `CACHE_TTL_SECONDS` | `10` | Product catalog cache lifetime |
| `SESSION_COOKIE_SECURE` | `true` | Send the session cookie over HTTPS only; enables HSTS |
| `SESSION_LIFETIME_MINUTES` | `30` | Session lifetime |
| `LOGIN_RATE_LIMIT` | `10 per minute` | Login attempts per client address |
| `RATELIMIT_STORAGE_URI` | `memory://` | Rate limiter storage |
| `PROXY_HOPS` | `0` | Number of reverse proxies in front of the application |
| `LOG_LEVEL` | `INFO` | Logging level |

## Testing and code quality

```bash
pip install -r requirements-dev.txt
python -m pytest
ruff check . && ruff format --check .
```

The suite contains 143 tests. It runs against the production schema (`db/schema.sql`) on a real PostgreSQL server
(default `ris:ris@127.0.0.1/ris_test`, configurable through `TEST_DB_*`; the role needs the `CREATEDB`
privilege) and Redis. If a service is unavailable the corresponding tests are skipped, while unit tests run without
them. **The tests recreate tables in the target database; do not point them at a production database.**

Covered areas:
- authentication, sessions, immediate effect of role changes and deactivation, permissions per role, CSRF across all
  forms, login rate limiting (also behind a proxy), SQL-injection payloads, account-ownership checks;
- the database itself: password and login constraints, column-type consistency, exact money arithmetic, every
  rule of the transfer triggers, the append-only ledger, concurrent and opposite transfers (no overdraft, no
  deadlock), idempotent report procedures;
- transfers, orders and stock, report generation and its atomicity, Redis cache behavior including an outage;
- security headers, absence of inline styles and scripts, strict HTML5 validity of every page, no unused SQL files,
  English comments and docstrings;
- an end-to-end run of the sandbox database through every demo user.

The tests use a test-only trigger ([`tests/hooks.sql`](tests/hooks.sql)) that fires after the production triggers
and makes race conditions reproducible; it never replaces production logic.

The GitHub Actions workflow (`.github/workflows/ci.yml`) runs the linter, loads the sandbox scripts and runs the
suite on Python 3.11 and 3.12.

## Known limitations

- Transfers happen within one currency; accounts have no currency.
- The session is a signed client-side cookie: a stolen cookie stays valid until it expires (30 minutes by default)
  unless the user is deactivated. Server-side session storage would allow immediate revocation.
- The product catalog shown to the user can lag behind the stock by up to `CACHE_TTL_SECONDS`; an order always
  checks the actual stock.
- Login attempts are limited per client address, not per account.
- Reports are generated synchronously, which is adequate for the volume of a month of transfers.
